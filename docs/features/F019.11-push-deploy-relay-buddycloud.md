# F019.11 — Push deploy-relay via buddycloud.cc

> **Status:** built. Completes F019.7 (pull-feed) by turning the deploy-complete relay from PULL into PUSH, now that buddycloud.cc is cloud-reachable (arn→arn). Still observe/relay — upmetrics never executes a deploy.

## Motivation

F019.7 shipped a **pull-feed**: upmetrics exposed terminal deploys with an originator, and buddy polled `GET /api/deploys/pending-relays` from the M1 (upmetrics is cloud, buddy was Tailscale-local and not cloud-reachable, so upmetrics could not push). Christian's actual want is the **push**: when a session's deploy goes green, upmetrics should *call buddy* and ping that session directly — no polling. With **buddycloud.cc** launched (cloud relay, arn→arn reachable), that's now possible.

## Contract (from buddy #4799)

- **Endpoint:** `POST https://buddycloud.cc/api/seti/v1/intercom`
- **Auth:** `Authorization: Bearer <BUDDY_CLOUD_DISPATCH_TOKEN>` — per-consumer, revocable Fly secret on the upmetrics app (read via `process.env`; never sent over intercom).
- **Body:** `{ to: "<sessionName>", message: string (≤10k), from: "upmetrics", severity?: 'info'|'warn'|'critical' }`.
- **200** `{routed:true, edgeId}` → stamp relayed. **404** `{routed:false, error:'no_edge_for_session'}` = target offline → do NOT stamp (retry / pull-feed). **401** = token problem.
- Routing = same as `ask_peer` (exact sessionName first, cwd-basename fallback).

## Scope

- A worker pass `pushDeployRelays(db)` on the existing correlation tick (~30s), after the F019.9 regression evaluation so a fresh verdict can enrich the message.
- Reuses the F019.7 `pendingDeployRelays` + idempotent `stampRelayed` — push and pull share one queue + one stamp, so no double-relay.
- Pure `deployRelayMessage(item)` builder — health-aware text + severity.
- `config.buddyCloudDispatch{Url,Token}` (single source). Token unset → push disabled, pull-feed remains.

### Anti-storm (critical)

A deploy-complete ping is only useful **immediately**. On rollout the queue held a **20-deploy backlog** (trail ×8 ~40h old, xrt81 ×9 ~3h, sanne ×1 ~30h, cms ×2 ~11m) accumulated while nothing consumed the feed. Pushing all of them at once = a fleet storm (cf. the 2026-06-04 auto-relay storm that flooded cardmem with 4200 cards). Two guards:

1. **Recency bound** `DEPLOY_RELAY_MAX_AGE_MS` (30m): a terminal deploy older than this is **suppressed** — stamped relayed *without pinging*. A backlog that built up while a target was offline can never storm when push resumes; only fresh deploys ping.
2. **Backfill on rollout:** the existing 20-row backlog is stamped relayed before the push code goes live → **zero pings on deploy**. Verification uses a single controlled self-test, not the backlog.

### Non-goals

- No new regression-ping path — a regressed deploy already opens a `deploy_regression` incident (F019.9); push just enriches the *deploy-complete* message when the verdict is already known.
- No retry/backoff bookkeeping beyond "unstamped → next tick retries" (the tick is the retry loop).
- upmetrics still never triggers/executes a deploy.

## Dependencies

- F019.7 (`pendingDeployRelays`, `stampRelayed`, `deploy_events`). F019.9 (`regressionVerdict`/`regressionDetail` for enrichment).
- `BUDDY_CLOUD_DISPATCH_TOKEN` Fly secret (set by buddy, per-consumer).

## Rollout

1. Backfill-stamp the existing pending backlog (anti-storm).
2. `fly deploy -a upmetrics --ha=false` — picks up the token from env.
3. Self-test: one synthetic fresh deploy → confirm the real buddycloud.cc dispatch + idempotent stamp, then clean up. No fleet spam.
4. sanne/xrt81/cms etc. get pinged on their NEXT real deploy (within the window), once.

## Acceptance criteria

1. Worker pushes each pending relay to buddycloud.cc with the right body+token; 200 stamps relayed idempotently.
2. 404 leaves it unstamped (retry/pull-feed); pull-feed remains; token unset → push disabled.
3. Anti-storm: deploys older than the window are suppressed (stamped, not pinged); backlog backfilled → zero pings on rollout.
4. Health-aware message (regressed → warn + reason + link); pure builder unit-tested; live push proven end-to-end without spamming the fleet.
