# F019.9 — Deploy regression detection (auto health-verdict)

> Turns F019 from deploy-**recording** into deploy-**monitoring**. OBSERVE / REPORT /
> RELAY only — v1 judges + relays + opens an incident; it NEVER auto-rolls-back or
> executes remediation. The actor stays where the authority is.

## Why

Today F019 records the status an app self-reports (`success`) and shows it. It does
not judge whether the deploy actually stayed healthy. Christian's "deployment-
monitoring" ask is exactly this: after a deploy lands, automatically answer *"did
this deploy regress?"* by correlating the deploy timestamp with the **error stream
upmetrics already ingests** (DSN). This is the Sentry "Releases" pattern and the
original rationale for homing deploy-observability in upmetrics (deploy↔error in ONE
platform). It was demonstrated manually for cardmem (#4463 retro) — this automates it.

## What it does

When an observed deploy reaches terminal **success**, upmetrics waits for a short
window (~15 min) to elapse, then compares the project's error stream AFTER the
deploy vs a baseline BEFORE it:

- **regressed** — after-window error count ≥ `MIN_AFTER` AND (after-rate ≥ baseline-rate
  × `MULTIPLIER`), OR a brand-new issue (fingerprint first-seen after the deploy)
  reaches ≥ `NEW_ISSUE_MIN` occurrences.
- **healthy** — otherwise.

regressed → opens a `deploy_regression` incident (flows into the existing alert
engine) + is surfaced on /deploys. The verdict also enriches the relay-ping once the
buddy poll/push path lands ("deploy <site> regressed — errors +X%").

## Architecture

- **Schema** (migration): `deploy_events` += `regression_verdict` (text null|healthy|
  regressed), `evaluated_at` (ts), `regression_detail` (json: before/after counts,
  new issues).
- **`deploys/regression.ts`**:
  - `computeVerdict(before, after, newIssues, cfg)` — PURE, unit-tested.
  - `pendingEvaluations(db, now)` — success deploys WHERE evaluated_at IS NULL AND
    updated_at ≤ now-WINDOW AND updated_at ≥ now-MAX_AGE (recency bound).
  - `evaluateDeploy(db, deploy, now)` — counts events(kind='error') for
    deploy.project_id in the after-window vs the baseline window, finds new
    fingerprints first-seen after the deploy, stamps verdict+detail+evaluated_at,
    and on `regressed` opens one `deploy_regression` incident (triggerRef=deploy.id).
- **Worker**: `evaluateDeployRegressions` runs inside the existing
  `startCorrelationWorker` tick (~30s) — no new daemon.
- **Surface**: `GET /api/dashboard/deploys` returns `regression_verdict`; the Deploys
  log renders a verdict badge (healthy = ok, regressed = down).

## Config (single source — DEPLOY_REGRESSION_*)

| Env | Default | Meaning |
|---|---|---|
| `DEPLOY_REGRESSION_WINDOW_MS` | 900000 (15m) | after-window observed post-deploy |
| `DEPLOY_REGRESSION_BASELINE_MS` | 3600000 (60m) | baseline before-window |
| `DEPLOY_REGRESSION_MULTIPLIER` | 3.0 | after-rate / baseline-rate ratio that flags |
| `DEPLOY_REGRESSION_MIN_AFTER` | 3 | min absolute after-errors to consider (noise floor) |
| `DEPLOY_REGRESSION_NEW_ISSUE_MIN` | 3 | a new fingerprint with ≥ this many post-deploy events flags |
| `DEPLOY_REGRESSION_MAX_AGE_MS` | 21600000 (6h) | never evaluate deploys older than this |

## Non-goals

- **No auto-action** (no rollback, no remediation execution) — observe/report/relay
  identity preserved. The bolder auto-act version is a separate, guard-railed decision.
- No per-tenant regression slicing (project-level in v1).
- `failure`-deploys are already known-bad; this is about `success` deploys that
  silently broke things.

## Rollout

Ship behind the existing worker; recency-bounded so it never retroactively alerts on
old deploys. Verdict visible on /deploys immediately; relay-ping enrichment lands
with the buddy push path (separate).
